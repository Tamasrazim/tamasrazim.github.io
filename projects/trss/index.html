INDEPENDENT NEURAL GRAPHICS RESEARCH / IN DEVELOPMENT

TrSS.

TrSS (Tamasrazim’s Real-time Scene Synthesis) is first-party neural-rendering research for Intel Arc GPUs. It explores guide-conditioned frame reconstruction and temporal stability, starting with an Intel Arc B580 target.

The long-term aim is a low-latency neural-rendering stage that complements a game’s existing renderer. The project now includes dataset tools, trainable first-party models, offline evaluation, native graphics API experiments, and a cooperative D3D11-to-OpenVINO bridge with a C++17 renderer host SDK. It is not yet a game-specific plug-in or a finished live-game renderer, and its output quality and performance have not been validated on the target GPU.

A renderer-guided reconstruction pipeline.

TrSS uses explicit renderer data and temporal context rather than guessing hidden scene information from a screenshot. The native bridge is cooperative: a host must submit the buffers and handle the returned frame.

01 / INPUT CONTRACT20 CHANNELS

Renderer guides + history

The model input combines noisy linear radiance, diffuse and specular albedo, normals, roughness, linear view depth, motion vectors, reprojected history RGB, and a history-validity mask. Coordinate spaces and motion conventions are checked explicitly.

02 / NATIVE BRIDGED3D11

Submit, validate, process

TrSSRRProcessLatestFrameV1 snapshots submitted FP16/FP32 textures, validates frame metadata and ranges, stages the buffers to CPU memory, packs the model tensor, and returns composed linear RGB to the host. The current path is synchronous and uses GPU-to-CPU readback.

03 / INFERENCEOPENVINO

Run the native model backend

The packaged backend loads a supplied static-shape model and the host-provided runtime directory. It executes the four-channel model head and composes a residual with the current frame using the history-validity gate. The repository does not include trained production weights.

What exists in the code.

The native frame path is now integrated and tested as a cooperative API. It is still separate from automatic game interception and production GPU validation.

01 / MODELFIRST-PARTY

Trainable reconstruction models

TrSS has a trainable 2× baseline and a separate guide-conditioned reconstruction graph. The guide-conditioned model accepts 20 channels and emits a four-channel residual/temporal-gate head. No trained production checkpoint is bundled.

02 / DATAPIPELINE

Generate and audit datasets

Includes synthetic scene generation, scene-separated manifests, provenance and guide-contract audits, resumable training, offline inference, and local visual review galleries. Representative game-renderer training data is still missing.

03 / HOST SDKC++17 / D3D11

Submit, reconstruct, upload

HostV1::process validates the immediate context, frame conventions, texture dimensions and device ownership. It submits the guide packet, runs the exact frame, uploads linear RGB into a host-owned RGBA32F shader-resource texture, and clears the processed packet. The engine still supplies its own G-buffer.

04 / BACKENDOPENVINO

Native inference library

A separate backend DLL is packaged with the Windows runtime. The OpenVINO runtime directory and a compatible trained model are supplied by the host machine; the automated end-to-end test uses a small deterministic CPU fixture.

05 / LIVE RUNTIMEDXGI

Windows graphics proxy

The current DXGI Present hook handles selected flip-model back buffers and conventional post-processing. It does not call the new reconstruction bridge or upload the reconstructed result into a game's presentation chain.

06 / TESTINGCI / WARP

Native bridge and SDK output test

Windows CI builds the runtime, backend, and host SDK, compiles the sample plugin shape, tests installer safety, and verifies output texture upload/readback with D3D11 WARP and a deterministic CPU fixture. This does not verify physical Arc GPU speed or visual quality.

What remains.

The open work is engine-specific integration, representative training data and hardware validation.

OPEN / 01ENGINE INTEGRATION

A real renderer plugin

An engine-specific plugin must map actual color, albedo, normals, roughness, depth, motion and reprojected history into the SDK contract. The SDK cannot discover or synthesize those buffers.

OPEN / 02TRAINING

Production data and trained weights

Capture representative renderer buffers, build session-separated targets, train the first-party model, and evaluate held-out scenes for image quality, temporal stability and failure cases.

OPEN / 03ENGINE + GPU

Render-graph composition and Arc B580 validation

The SDK uploads linear RGB into a host-owned FP32 texture. An engine-specific plugin must sample it at the correct render-graph stage, apply the engine’s tone mapping and present normally. The synchronous staging path still needs performance work and physical Arc B580 validation.

Native bridge and host SDK milestone completed; live renderer still in development.

The D3D11-to-OpenVINO bridge and host-side FP32 output upload pass automated WARP integration tests. An engine-specific plugin, production model weights, engine render-graph composition, and physical Arc B580 validation are still outstanding.

NATIVE GAME / WINDOWS X64 / C++20

TUNRUN.

A seed-driven 3D tunnel-flight game about reading the course, controlling your spacecraft, and surviving an environment that is generated instead of memorised.

TUNRUN is being built as a native Windows game—not a browser demo. The current source contains a playable-system prototype and several real deterministic game systems. It is still in development, and this page separates what exists now from what remains on the roadmap.

01 / IMPLEMENTED SYSTEMS

The prototype features.

These describe systems present in the current project source and documentation, not promises that the final balance or hardware acceptance is complete.

01.1 / PROCEDURAL COURSE

Seeded tunnel geometry

Implemented baseline

Stateless 64-bit hash streams derive centerline control offsets, bounded tunnel radii and twist from the root seed, node index and parameter channel. Catmull–Rom interpolation smooths the course between control points spaced 18 normalised course units apart. The renderer and tunnel-wall check sample the same course source.

Canonical course hashes and parameter-range validation are exposed in Seed Lab. Current geometry is a forward-aligned lateral/vertical path; stable tangent-aligned 3D frames, advanced taper/flare transitions and broad cross-section variety remain unfinished.

01.2 / GATES

Four generated aperture gates

Implemented baseline

Generator v2 makes Standard, Precision, Offset and Wide gate families from seed-derived parameters. Family-specific aperture and offset envelopes are validated, with independent obstacle hashes and distinct visual cues.

Validation includes an all-ship adjacent-gate kinematic screen and a fixed-step route probe that follows one concrete trajectory through consecutive gates. It is a tested witness path—not an exhaustive proof that every possible state is recoverable.

01.3 / MOVING HAZARDS

Deterministic mine field

Implemented baseline

Moving 3D mines use seed-derived baseline positions, horizontal and vertical oscillation, speed, phase and collision radius. Hazard motion is reproducible from the seed and run clock. Four seed-selected visual families—Orbital, Prism, Rotor and Cross—have distinct silhouette/color treatments, and the HUD names the next family. These are cosmetic variants of the same mine physics.

Contact uses a swept relative 3D closest-approach test transformed into course-relative coordinates. The current validator checks parameter bounds and separation from gate reaction windows. Additional physical hazard behaviours and hardware-verified reaction timing remain planned.

01.4 / PICKUPS

Two deterministic resources

Implemented baseline

Aether Shards begin at distance 20 and repeat every 24 distance units. Each pickup yields a seed-determined 4–8 shards. Every eighth pickup is a Singularity Core worth one core.

Pickups use swept forward-plane crossing and the sampled course-relative frame shared by the tunnel renderer. Rewards are capped, currency arithmetic saturates safely, and a missed pickup cannot be collected by flying backward through it.

01.5 / SCORING

Precision gates and combo chains

Implemented baseline

Each gate family has its own base score: Standard 100, Precision 180, Offset 140 and Wide 80. Accuracy adds up to 100 points; a clean pass adds 75 more. Clean means at least 70% of the safe aperture accuracy value.

Combos increase the multiplier by 0.1× per existing combo level, capped at 5×. Invalid/non-finite crossings are rejected, scores saturate at a safe cap, and current career-best score and combo persist in profile v3.

01.6 / DASH

Short energy dash

Implemented baseline

The dash is edge-triggered for 0.24 seconds, costs 28 energy and has a 1.20-second cooldown. It adds a 19-unit/s forward burst, or 24 units/s while also boosting. Dash cannot activate while precision mode is held.

The 120 Hz fixed-step simulation advances dash timing so render frame rate does not decide its duration. Visual dash streaks and HUD cooldown cues are specified as feedback.

01.7 / FLIGHT

Fixed-step steering and collision

Prototype system

Lateral and vertical flight updates use a fixed 120 Hz simulation, bounded steering and acceleration, boost energy and precision mode. The tunnel wall check uses the seeded course sampler; a retry path is present.

The camera look target follows ship yaw/pitch in both FPP and TPP and clamps its cross-section offset inside the tube. Flight tuning, multi-state route reachability, broader seed validation and multi-machine acceptance remain in progress.

01.8 / SEED LAB

Inspect and reproduce runs

Implemented baseline

The Seed Lab reports course, gate, mine and reward hashes with validation summaries. Its selected-ship route diagnostics now include a bounded 32-state graph that branches viable gate-crossing states into multiple target policies and reports gates cleared, peak beam width and gates with multiple passing states. This is broader empirical trajectory coverage, not an exhaustive proof of all reachable states. Gate/mine crash reports include the deterministic obstacle index and distance to aid reproduction.

Text seed input accepts 1–64 letters, digits, spaces, underscores or hyphens; normalises text before hashing, and supports literal hexadecimal seed values. The chosen root seed is saved before a run starts.

01.9 / LOCAL PROFILE

Save, migrate and recover

Implemented baseline

Profile v3 has 18 fields, bounded parsing up to 64 KiB, strict key/type/range checks and an FNV-1a checksum for accidental-corruption detection. Valid v1 and v2 profiles are migrated through version-specific validation.

Writes use a same-directory temporary file and atomic replacement, retain a backup, and offer explicit recovery while preserving corrupt copies. The Windows save directory is marked Hidden where supported; that is convenience, not encryption.

ECONOMY RULES

Local, play-earned unlocks

No real-money purchase system is planned. A purchase validates ship id and wallet balance, changes the candidate profile, and must be rolled back if persistence fails. These are local progression values, not online anti-cheat security.

04 / RUN LOOP / PROGRESSION

From seed to result.

The implemented systems already connect reproducible generation, flight, scoring, pickups and local records. Campaign breadth and several advanced modes remain design targets.

01 / PREPARE

Choose and seed

Choose a ship, use a random or literal seed, inspect deterministic hashes in Seed Lab, and persist the root seed before the run begins.

02 / FLY

Read the tunnel

Steer through curved, twisted and changing-radius course samples, pass aperture gates, avoid moving mines, manage boost and collect rewards.

03 / SCORE

Play clean

Gate accuracy, clean-pass bonuses and combo multipliers reward precision. Pickup totals and score records are updated at run end under capped arithmetic.

04 / RECOVER

Keep the profile

The local profile saves settings, ship unlocks, currencies, run/crash totals, best distance, career-best score/combo, seed and run serial.

05 / REPEAT

Reproduce a failure

Repeat the same seed to replay deterministic course/hazard rules. Crash diagnostics show gate or mine index and distance to aid debugging.

05 / LOCAL DATA / RELIABILITY

Progress that survives.

The current save implementation focuses on preventing accidental data loss; it is not encryption and not an anti-cheat boundary.

PROFILE FORMAT

Strict schema v3

Exactly 18 fields. The parser rejects duplicate, missing or unexpected keys, validates data types and numeric ranges, rejects non-finite values and caps input at 64 KiB.

INTEGRITY

FNV-1a checksum

Detects accidental profile corruption. It is not cryptographic signing, encryption, tamper resistance, or a trustworthy anti-cheat mechanism.

MIGRATION

v1 / v2 → v3

Older profile versions are validated against their own schema/checksum rules before migration. A good pre-migration copy is retained.

ATOMIC WRITE

Temporary file + backup

Writes flush a same-directory temporary file before replacing the primary. The backup can recover a corrupt primary; damaged copies are preserved with a corruption suffix when both fail.

LOCAL PATH

Per-user Windows storage

%LOCALAPPDATA%\Tamasrazim\TUNRUN\profile.json plus profile.bak. Hidden attributes are applied where supported as a convenience only.

NOT IN SCHEMA V3

Known persistence gaps

Campaign checkpoints, achievements, ghosts, full input bindings, timestamps and mode-specific records remain future migrations—not fields that the current profile already saves.

06 / ART / AUDIO / COMFORT

Visual direction and remaining polish.

The established art direction is restrained, high-contrast tunnel geometry and legible hazards; the project has not reached final asset production.

ART DIRECTION

Graphite, silver, signal white

Forward perspective, expanding spatial frames, clean silhouettes and luminous edge cues. Course geometry should feel composed from procedural rules—not random piles of primitive shapes.

CURRENT ART

Wireframe prototype ships

Eight procedural third-person silhouettes and matching 2D hangar previews are rendered in raylib. These are prototype visualisations, not final production meshes/materials.

AUDIO PLAN

Engine, hazards, rewards

Planned sound families include propulsion, boost/dash, tunnel ambience, warning cues, collision, pickup, menu and results feedback. Final sound assets/mix are unfinished.

ACCESSIBILITY

Control and motion comfort

Settings/targets include mouse sensitivity and inversion, gamepad dead-zone/response, FOV, camera distance, audio and graphics settings, reduced motion and screen-shake controls. Full tested accessibility remains unfinished.

07 / REMAINING WORK

What has not shipped yet.

The roadmap advances only when code, tests and real Windows acceptance support it. A screen existing does not by itself mean the feature is finished.

  • Extend the bounded 32-state graph with a broader control-policy sample and more deterministic seed fixtures; it is not yet an exhaustive reachability proof.
  • More dynamic hazard families and route-dependent rewards.
  • Asynchronous streaming and bounded-memory endless runs.
  • Hardware-verified reaction/warning distances and collision/render agreement.
CONTENT

Full game modes

  • Campaign checkpoints, stage completion and difficulty tiers.
  • Endless, practice and daily rules/records.
  • AI pilots, environmental drones and event entities.

PRODUCTION

  • Final production ship models, materials and sound design.
  • Complete input remapping and Windows DPI/fullscreen mouse QA.

TUNRUN is not yet advertised as a finished game or a release download. Its release artifacts are planned as a Windows installer and portable package after the build, test, input, persistence, asset-license and clean-machine acceptance gates pass.

08 / BUILD / TEST / PRIVACY

Technical and engineering notes.

TUNRUN is offline-first by design. Ordinary gameplay should not require accounts, telemetry, ads, remote services, elevated privileges or downloaded executable content.

BUILD

Windows x64 / CMake

Toolchain: Visual Studio 2022 / MSVC, CMake 3.21+, C++20 and pinned raylib 5.5. Run the repository's Windows workflow as the source of truth for build/test status.

cmake --preset windows-dev
cmake --build --preset windows-dev
ctest --preset windows-dev

AUTOMATED QA

Deterministic regression tests

Source tests cover input state, profile validation/migration, economy transactions, seeded geometry/gates/mines/rewards, scores and swept-contact edge cases. The documented regression suite includes multi-seed batches and ship-specific gate probes; these do not replace full hardware testing.

SECURITY

Bounded, local data

Save parsing has strict size/type/range limits. Corruption is handled with backup/recovery, local saves remain under the current Windows user profile, and the project does not claim hidden files are secure. No account or online multiplayer system is planned for the first release.

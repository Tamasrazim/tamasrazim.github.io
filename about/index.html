01 / BIOGRAPHY

Still learning.
Still building.

My work sits where software and creativity meet. I like exploring how an idea can become a real tool: a browser-based animation renderer, a game system, a desktop utility, a graphics experiment, or a collection of reusable visual assets. I often think in terms of the whole product—not just one feature, but its interface, workflow, file formats, documentation, performance, and how another person would actually use it.

I'm not presenting myself as an all-knowing engineer. I'm learning, testing ideas, working through bugs, and developing my technical judgement through projects. Some ideas are ambitious and some are still prototypes. I want the site to make those distinctions clear rather than dress every experiment up as a finished product.

I also create and publish visual assets. That work gives me another way to explore motion, vector shapes, repeatable loops, metadata, and practical delivery formats. Software and creative work are not separate worlds for me: tools can make creative work easier, and creative projects can expose what a tool still needs to improve.

03 / INTERESTS & WORKING STYLE

What keeps me curious

My recurring interests include PC hardware and performance, Windows software, graphics technology, gaming, procedural systems, web interfaces, motion design, vector formats, video creation, and tools that work without unnecessary account or subscription requirements.

I tend to care about the entire workflow. A feature is not much use if its button does nothing, the output file is broken, the interface hides the important settings, or the documentation overpromises. That is why project plans often include usability, rendering, file export, performance, error handling and clear status—not only the headline feature.

I prefer direct language and evidence over inflated titles. I can be interested in a difficult technical area without claiming I have already solved it. The experiments are part of the journey, and the unfinished parts deserve honest labels too.

01TRILYVACreative software · Browser-based animation renderer+
In developmentAnimationVector export

TRILYVA is my direction for a browser-based, code-driven animation renderer. The aim is to let a creator write or edit JavaScript animation, preview it, configure a render, and export usable media from one focused workflow.

The planned workflow includes code, preview, render settings, confirmation, rendering progress, a small waiting-time mini-game, completion and download. I want support for transparent backgrounds, 16:9 output, different clip durations, SVG and EPS/vector delivery, transparent PNG sequences or images, MP4 output, and metadata where the relevant renderer pipeline supports them.

My current target includes high-resolution, high-frame-rate rendering and frame-by-frame evaluation. A stated target such as 16K at 240 fps is not a guarantee that every device, browser, animation or export format will sustain that rate. Real output depends on scene complexity, memory, browser limits and encoding. The priority is to render frames deliberately without silently skipping animation states.

TRILYVA grows out of my earlier Code Motion work. I also want it to support richer layered 2D and 2.5D cartoons, reusable animation libraries, and better vector editing rather than only simple demonstrations.

03TUNRUNProcedural 3D tunnel-runner game+
In developmentGame systemsProcedural world

TUNRUN is a tunnel-running game concept built around a curving, endless route rather than a flat straight track. The design direction includes procedural curves and noise, an inside-the-tunnel camera, third-person and first-person perspectives, obstacles, a controllable ship, and collectable coins or gems.

The intended feel is fast and spatial: the route should bend, the camera should communicate movement, and obstacles should require attention. Input, collision, progression, interface, saving and procedural generation all need to work together. This entry describes the intended design, not a claim that every system is finished.

10WEBEDYTSDesktop website editor concept+
In development / designDesktop softwareVisual editing

WEBEDYTS is my concept for a desktop website editor that lets people work visually with an existing site's pages. The direction is to load a site's index and adjust text or interface placement without requiring the user to manually edit HTML or JavaScript for every change.

The broader plan includes searchable animation presets, multiple desktop operating systems and architectures, and export workflows for media such as video, PNG, SVG and GIF. These are project goals, not a statement that every platform or format is already implemented. A central challenge is to keep visual editing useful without unexpectedly damaging the original site's structure or behavior.

14TrSS Sample RecorderWindows graphics data-collection utility+
Separate utilityWindowsGraphics telemetry

The TrSS Sample Recorder is a separate utility concept intended to collect structured graphics-performance samples from supported, installed games. The design direction includes a native Windows interface, a library view based on detected games, capture sessions, and JSON output with a controlled file size.

The recorder is not the same thing as the TrSS rendering experiment. It is meant to help collect observations for analysis; it does not itself prove an upscaling or neural-rendering improvement. Compatibility, measurement quality, game safety and the actual capture implementation need to be validated for each setup.

Open Sample Recorder page ↗
15TrSSExperimental graphics research+
Research / prototypeGraphicsIntel Arc focus

TrSS stands for Tamasrazim's Super Sampling graphics Technology. It is an experimental graphics project exploring ideas around image reconstruction, super sampling and neural-rendering-style improvements, with a focus on Intel Arc hardware.

The long-term ambition goes beyond a simple resolution scaler, but ambition is not the same as demonstrated results. A credible graphics system needs working integration, reproducible before-and-after comparisons, performance measurements, image-quality evaluation and compatibility testing. TrSS should be considered experimental until those results are available.

The Sample Recorder is a separate project intended to support data collection. It should not be confused with a completed TrSS renderer or with verified support across games and graphics APIs.

05 / PRINCIPLES

How I want to work

Be honest about status. A prototype, an active development project and a finished release are different things. I want visitors to know which one they are looking at.

Build for actual use. Interfaces, exports, documentation, reliability and accessibility matter alongside ambitious features.

Keep learning visible. I don't need to pretend I know everything to work on challenging ideas. Progress includes fixing mistakes, testing assumptions and revising plans.

Respect creative ownership. I care about making my own assets, understanding the formats I publish, and being clear about how software and media may be used.
